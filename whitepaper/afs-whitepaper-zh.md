## 1. 引言

我们正在见证人类与软件交互方式的范式转变。自主 AI 智能体的崛起——它们具备推理、规划和执行多步骤工作流的能力——要求我们从根本上重新思考软件设计。今天的软件是为人类构建的，AI 智能体被迫在这种以人为中心的环境中导航，浪费了大量资源，引入了安全漏洞，并产生了不可靠的结果。

**AFS（AI/Agent-Friendly Standard，智能体友好标准）** 是一个开放规范，它颠覆了这一局面。AFS 不是让 AI 去适应人类软件，而是定义了软件应当如何从底层设计，使其成为 AI 智能体的好工具。AFS 提供了通用词汇、分层架构和轻量级约定，使任何服务或工具都能达到"智能体就绪"状态——实现安全、高效、可靠的交互。

本白皮书阐述了 AFS 的设计动机、核心设计哲学、技术架构以及在更广泛的 AI + 软件生态系统中的定位。规范性技术规格请参见 [`spec/overview.md`](../spec/overview.md)。

## 2. 问题：AI + 软件交互的四种困境

### 2.1 屏幕级操作——让 AI 模仿人类

当前的一类思路是让 AI "学会"使用人类软件——通过截图、模拟点击和浏览器自动化。这种方法有三个致命缺陷：AI 必须处理大量截图和 UI 元数据，Token 消耗极其高昂；页面超时、按钮定位失败、布局变化等问题导致操作频繁失败；许多网站部署了反机器人措施，主动封禁自动化访问。

**核心瓶颈：可靠性极差，成本极高。**

### 2.2 应用内嵌 AI——碎片化的孤岛

另一类思路是每个产品嵌入自己的 AI 助手：Zoom 有自己的 AI，Miro 有自己的 AI，N8N 有自己的 AI。这造成了严重的碎片化：十个应用意味着十个独立的 AI，彼此互不知晓。Zoom AI 总结了一场会议，但要让 Miro AI 根据这些笔记创建看板，仍然需要手动复制粘贴。用户在每个应用中为本质相同的 LLM 能力重复付费，跨应用编排几乎不可能实现。

**核心瓶颈：上下文割裂，无法跨应用协作。**

### 2.3 MCP 与工具驱动架构——Token 爆炸

许多软件厂商开始提供官方的 MCP 工具集，将 API 封装为工具供 AI 调用。MCP 协议本身支持动态工具发现，其设计方向是正确的。然而，**当前主流的 MCP 使用模式**存在严重问题：大多数 MCP 服务端实现将所有接口一次性暴露，缺乏按场景裁剪的工具组织策略。当一个通用智能体需要同时接入代码库、文档管理、日程安排等多个领域时，光是工具名称、参数 Schema 和使用说明就消耗大量 Token，初始化的代价和延迟极其可观。

## 3. AFS 规范（Agent-Friendly Standard）

**AFS** 是一套开放规范，定义了怎样的软件架构才能让 AI 智能体最高效、最安全、最精准地调用。它不创造新的 AI 模型，而是回答一个基础问题：**软件如何成为 AI 的好工具？**

### 3.1 工具的三层构成

每个符合 AFS 标准的工具由三个层次构成，共享同一套核心逻辑：

| 层次 | 性质 | 说明 |
|------|------|------|
| **API** | 核心逻辑层 | 结构化输入输出，所有操作的唯一真实来源。CLI 和 GUI 都是它的封装。|
| **CLI** | 智能体操作通道 + 开发者调试接口 | API 的标准化命令行封装。AI 通过 CLI 执行操作，开发者用它调试和编写脚本。|
| **GUI（可选）** | 人类观察通道 | 用于人类监督和检查 AI 的工作成果，遵循双通道架构（见 §3.6）。|

智能体通过 skill.md（见 §3.3）了解工具能做什么，通过 CLI/API 执行具体操作。GUI 不是 AI 的入口——它是人类的监控屏幕。

### 3.2 为什么是 CLI 而非纯 API 调用？

一个自然的问题：既然 API 本身就是结构化的 JSON 输入输出，为什么 AFS 还要在 API 之上封装一层 CLI，而非让智能体直接调用 API？

原因有三个：

**第一，操作系统级别的沙箱与权限控制。** CLI 进程天然运行在操作系统的进程模型之下，可以直接利用已有的成熟安全基础设施——容器隔离、文件系统权限、用户身份切换、seccomp 沙箱等。直接 API 调用则需要在应用层自行实现全部安全逻辑。将操作封装为 CLI 命令，意味着每次调用都是一个独立进程，可以被操作系统级别的安全策略约束，爆炸半径被限制在单个进程内。

Jerry：seccomp 沙箱 -> 基于BPF技术的轻量级沙箱
       爆炸半径被限制在单个进程内 -> 即使安全漏洞被成功利用，爆炸半径被限制在单个进程内

**第二，可审计性与可组合性。** CLI 调用天然产生可读的执行日志（命令 + 参数 + 输出），人类和自动化系统都可以直接审计。CLI 命令可以通过管道组合，支持 Unix 哲学的工具编排。这种可组合性正是 AI 智能体编排多工具时所需要的。

**第三，语义密度。** 设计良好的 CLI 命令（如 `afs-crm contact list --status active --limit 10`）本身就是一段自然语言级别的操作描述。LLM 可以生成、阅读和推理 CLI 命令，其语义密度远高于等价的 JSON API 请求体。这直接减少了 Token 消耗，也降低了生成错误调用的概率。

需要强调的是：CLI 是 API 的**封装层**，不是**替代品**。所有业务逻辑仍由 API 层承载，CLI 是智能体与 API 之间的标准化、安全化的操作通道。

### 3.3 开发者提供的skill.md: （以AFS标准开发的）应用能力描述文档

skill.md 是每个 AFS 工具必须提供的**机器可读能力描述文件**。它是AI Agent理解以AFS为标准而开发的应用的唯一入口，等同于该应用的“说明书“

Jerry：是每个 AFS 工具 -> 是每个基于AFS规范/标准开发的工具/应用（我觉得应用更好，可以这个文章里统一口径）

**格式要求：** Markdown 格式，采用固定的层级结构。工具开发者负责编写和维护。

**层级结构（渐进式披露）：**

| 层级 | 内容 | 加载时机 | 用途 |
|------|------|---------|------|
| **L0 — 概述** | 一句话描述 + 核心命令列表（名称与简介） | 工具安装时自动注入上下文 | 智能体判断该工具是否与当前任务相关 |
| **L1 — 能力** | 每个命令的参数、输入输出格式、基本用例 | 智能体决定使用该工具时按需加载 | 完成基本操作 |
| **L2 — 示例** | 多步骤工作流示例、常见组合模式 | 遇到复杂任务时按需加载 | 处理非平凡场景 |
| **L3 — 高级** | 边界情况、高级配置、性能调优 | 极少加载 | 专家级使用 |

**设计原则：** 每一层都应可独立使用——读完 L0 能判断要不要用，读完 L1 能完成基本操作。层级之间不应有强依赖，AI 不必阅读 L2 才能理解 L1 的内容。

与传统 API 文档（如 OpenAPI/Swagger）的区别在于：skill.md 面向 LLM 优化，优先语义清晰度而非形式完整性，强调渐进式加载以最小化 Token 开销。

### 3.4 紧凑响应——只返回必要数据

CLI 默认返回精简格式，仅包含最关键的字段。完整信息通过 `--verbose` 或 `--fields` 参数按需获取。每个多余的字段都在消耗 Token 和上下文空间。

示例对比：

```
# 默认输出（紧凑）
$ afs-crm contact list --status active
ID      Name          Status
C-0012  Alice Zhang   active
C-0034  Bob Li        active

# 详细输出（按需）
$ afs-crm contact list --status active --verbose
ID      Name          Email              Phone         Created     Status
C-0012  Alice Zhang   alice@example.com  +86-138-xxxx  2026-01-15  active
C-0034  Bob Li        bob@example.com    +86-139-xxxx  2026-02-03  active
```

### 3.5 启动时加载——打开即就绪

用户打开 以 AI/Agent 友好标准 (AFS) 开发的软件时，skill.md 的 L0 层（一句话描述 + 核心命令列表）自动注入智能体上下文，跳过工具检索环节。详细文档在 AI 决定使用该工具时按需加载。

这直接回应了 §2.3 中描述的 Token 爆炸问题：智能体在启动时只承担每个工具约几十 Token 的 L0 描述成本，而非一次性加载全部 Schema。

### 3.6 语义化设计——命令即文档，错误即指引

**语义化 CLI：** LLM 天然具备语义理解能力。CLI 命令和参数应使用完整的动词短语和自然语言值（如 `--status active` 而非 `--s 1`），使 AI 无需查阅文档即可推断命令含义，大幅精简说明文档篇幅。

**语义化错误信息：** CLI 的错误输出应包含错误类型、原因和建议的修正操作，使 AI 无需回查文档即可自主纠错。

示例：
```
$ afs-report generate --quarter March
Error [INVALID_VALUE]: --quarter expects Q1-Q4, got "March".
Suggestion: Did you mean --quarter Q1?
```

### 3.7 AFS 合规分级

AFS 定义了三个合规等级，等级越高，对 AI 越友好。每一级都有独立价值，级别之间严格递进：

| AFS 分级 | 要求 | 解决的问题 |
|---------|------|-----------|
| **AFS-1（可调用）** | API + skill.md（至少包含 L0 和 L1 层级） | AI 可调用工具并理解如何使用，门槛最低 |
| **AFS-2（安全可控）** | 在 AFS-1 基础上，核心功能与高风险操作须封装为 CLI (例如对系统关键文件的读/写/编辑/删除)，并在 skill.md 中标注操作的风险等级；其余低频操作可保留纯 API 访问 | 关键操作有架构级安全边界，同时保持灵活性 |
| **AFS-3（可监督）** | 在 AFS-2 基础上，提供 GUI 观察通道，CLI 执行的状态变更实时同步到 GUI | 人类可通过 GUI 观察 AI 操作，可随时介入 |

**关于 AFS-2 的风险等级划分：** AFS-2 要求工具开发者在 skill.md 中为每个操作标注风险等级。标准提供以下三级分类作为基线指引：

| 风险等级 | 定义 | 示例 |
|---------|------|------|
| **read** | 只读操作，不改变系统状态 | 查询列表、获取详情、导出报告 |
| **write** | 创建或修改数据，可撤销 | 创建记录、更新字段、重命名文件 |
| **destructive** | 不可逆操作或涉及敏感资源 | 删除数据、修改权限、发送邮件、执行支付 |

工具开发者可以在此基线之上细化自己的风险分类，但 skill.md 中必须包含每个命令的风险等级标注。智能体或编排平台据此决定哪些操作可自动执行、哪些需要人类确认。

## 4. 安全模型

安全性是 AFS 最重要的设计维度之一。§2.4 揭示的 OpenClaw 权限失控问题说明：如果没有架构级别的安全约束，AI 智能体越强大，风险就越大（例如系统提示词注入攻击等）。AFS 的安全策略基于以下四个层次：

### 4.1 进程级隔离

每个 CLI 命令调用是一个独立进程，运行在受限的执行环境中。工具开发者应支持将 CLI 运行在容器、沙箱或受限用户身份下（开发者在提供的skill.md（说明书）里注明自己的应用中哪些是高危操作，Agent通过学习skill来将高危操作运行在沙箱中）。智能体无需获得系统级 Shell 权限——它只能通过预定义的 CLI 命令与系统交互，每个命令的输入空间、输出格式和副作用范围都是确定的。

举一个例子，假设让基于LLM的agent煮饭，有以下两种方法：1. 给他生火工具，刀具和厨具和食材，所有操作都需要机器人自身来做--使用刀具，点火等等 2.我提前搭建好一个做饭机器，预留好一个“做饭”按钮，只要将食材放进机器按下按钮即可，剩下的交给做饭机器来。Agent有且仅有按下按钮的权限。

这两种方案的风险以及可靠度孰优孰劣是不言而喻的。方案一中大部分的不确定性和风险都被封装进了方案2中的 做饭机器中（也就是cli ）。假使此Agent遭遇提示词攻击，采取方案一和方案二所产生的后果也是天差地别的。

Jerry：这两种方案的风险以及可靠度孰优孰劣是不言而喻的 ->这两种方案的风险暴露面的差距是不言而喻的

与 OpenClaw 模式的对比：OpenClaw 授予智能体一个完整的 Shell，智能体可以执行任意命令（`rm -rf /`、`curl` 外传数据、修改 SSH 密钥）。AFS 模式下，智能体只能调用工具声明的 CLI 命令集，攻击面被收缩到工具 API 的边界内。

### 4.2 风险标注与操作确认

如 §3.7 所述，每个操作在 skill.md 中标注风险等级。编排层（智能体框架或 AFS Shell）可据此实施策略：read 操作自动执行，write 操作记录日志，destructive 操作需要人类确认。这将安全决策从"是否信任智能体"转变为"是否信任这个具体操作"，粒度更细，风险更可控。

### 4.3 输入验证与提示注入防御

语义化 CLI 的一个安全优势在于：参数空间是预定义的、有限的。`--quarter` 参数只接受 Q1-Q4，`--status` 只接受 active/inactive——这些约束在 CLI 层面即可强制执行，不依赖 LLM 的判断。相比之下，直接将用户输入拼接到 API 请求体中，更容易受到提示注入攻击。CLI 的参数验证机制为提示注入提供了一道架构级别的防线。

Jerry：提示注入攻击通常是针对大模型的推理阶段的攻击手段，”直接将用户输入拼接到 API 请求体中“这里可以再确认下是否受用

### 4.4 可审计性

CLI 调用天然生成结构化的执行记录：时间戳、命令、参数、返回码、输出摘要。这些日志可以被安全团队审计、被自动化规则扫描、被回滚机制引用。在企业合规场景中，"AI 做了什么"的可追溯性往往是部署的前提条件。

## 5. 核心价值

以下逐项说明 AFS 如何系统性地解决 §2 中提出的四类困境：

### ① Token 节省——更低成本，更快响应，更高推理准确率

**回应 §2.1 屏幕级操作的高成本 + §2.3 MCP 工具爆炸。**

通过三个机制协同降低 Token 消耗：结构化 CLI 替代截图和 UI 元数据（回应 §2.1）；紧凑响应格式只返回必要数据（§3.4）；skill.md 的渐进式披露确保智能体只加载当前任务所需的文档层级（§3.3 + §3.5），而非一次性吞入所有工具 Schema（回应 §2.3）。更短的上下文窗口意味着更低的 API 调用成本、更快的响应速度，以及——关键地——更高的 LLM 推理准确率。

### ② 安全内建——架构级约束，而非信任假设

Jerry：安全内建——架构级约束，Agent零信任

**回应 §2.4 OpenClaw 的权限失控。**

AFS 的安全模型（§4）从四个层面收缩攻击面：进程级隔离限制单次调用的爆炸半径；风险标注将安全决策下沉到操作粒度；CLI 参数验证为提示注入建立架构防线；执行日志确保可审计性。这套机制的核心思想是：**不信任智能体不会犯错，而是让架构本身限制错误的后果**。

### ③ 可靠性——结构化接口替代脆弱的屏幕解析

**回应 §2.1 屏幕级操作的高失败率。**

CLI 的输入输出是确定性的：命令格式固定、参数类型明确、输出结构可预期。不再有"按钮找不到"、"页面超时"或"输出格式意外变化"的故障模式。在企业场景中，操作的可靠性和可预测性往往比成本更具决策影响力。

### ④ 统一入口，共享上下文，跨工具协作

**回应 §2.2 应用内嵌 AI 的碎片化。**

单一 AI 智能体编排所有 AFS 工具，上下文自然共享。用户不再需要在不同应用的 AI 助手之间手动复制粘贴，也不再需要为每个应用单独付费购买 AI 功能。一场会议的总结可以直接成为项目管理工具创建任务的输入——因为它们共享同一个智能体的上下文。

### ⑤ 智能体无关，最大可移植性

AFS 工具不绑定任何特定智能体框架。无论是 OpenClaw、Claude Code、Open Code，还是任何新框架——只要它能读取 skill.md 并执行 CLI 命令，就能使用 AFS 软件。这保护了工具开发者的投入：一次适配，所有智能体可用。

## 6. 与 MCP 的关系

AFS 与 MCP（Model Context Protocol）不是竞争关系，而是互补关系。

**MCP** 定义了智能体与工具之间的**通信协议**——消息如何传递、工具如何注册、结果如何返回。它解决的是"智能体和工具如何对话"的问题。

**AFS** 定义了工具本身的**设计规范**——API 如何组织、能力如何描述、安全边界如何划定。它解决的是"工具如何成为好工具"的问题。

一个类比：MCP 相当于 HTTP 协议，AFS 相当于 RESTful API 设计规范。HTTP 定义了请求如何传输，REST 定义了 API 应当如何设计。两者解决不同层次的问题，且最佳实践是同时采用。

一个符合 AFS 规范的工具完全可以通过 MCP 协议暴露给智能体。事实上，AFS 的 skill.md 渐进式披露设计可以作为 MCP 工具发现机制的增强——在 MCP 的工具列表中只返回 L0 层描述，在智能体选择工具后再加载完整的 L1/L2 文档。

## 7. 未来路线图

AFS 仍在持续修订中。以下是我们对未来发展方向的规划：

### 7.1 AFS 软件市场

建立一个开放的 AFS 工具市场。所有上架工具须经过开源社区的安全审查与 AFS 合规等级验证，确保智能体可以安全调用。市场提供一键安装服务，降低用户和智能体的接入成本。

### 7.2 AFS Shell——统一操作入口

当前操作系统的入口是图形桌面：用户通过点击图标启动应用、通过窗口切换管理任务。AFS Shell 将这一范式 CLI 化——它是一个面向 AI 智能体的命令行操作环境，所有软件管理操作（安装、启动、卸载、配置）统一通过 CLI 完成。AI 智能体在 AFS Shell 中编排多个 AFS 工具，就像开发者在终端中编排多个命令行工具一样自然。

用户可以自由接入任何 LLM API 作为驱动智能体，不绑定任何单一模型提供商。

### 7.3 更大的愿景：迈向 Agent OS

我们正在见证一场不可逆的行业转变：从"软件 + 内嵌 AI"的捆绑模式，转向 **AI 是入口和中枢，软件成为 AI 的插件**的新范式。

AFS 的终极愿景是成为 **Agent OS** 的基础层：

| 操作系统类比 | AFS 对应 |
|------------|---------|
| 内核系统调用规范 | AFS 规范（工具如何设计） |
| 应用商店 | AFS 软件市场（工具如何分发） |
| Shell / 桌面环境 | AFS Shell（智能体如何操作） |

正如操作系统定义了应用与硬件交互的规则，AFS 定义了 AI 智能体与软件工具交互的规则。随着更多软件采用 AFS，一个以 AI 为中心的软件生态将自然涌现。

从技术路径上看，实现 Agent OS 需要依次完成三个里程碑：首先是 AFS 规范本身的稳定和采纳（当前阶段）；其次是 AFS Shell 的实现和工具市场的建立；最后是操作系统级别的集成——将 AFS Shell 作为系统原生的智能体交互层。每个阶段都独立可用，后一阶段建立在前一阶段的基础之上。
