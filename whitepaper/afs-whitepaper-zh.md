# AFS 白皮书 v0.1 — Agent-Friendly Standard

*"别教 AI 适配人类软件，要让软件为 AI 而生。"*

*版本：* 0.1（草案）
*状态：* 进行中
*日期：* 2026 年 3 月

---

## 1. 引言

我们正在见证人类与软件交互方式的范式转变。自主 AI 智能体的崛起——它们具备推理、规划和执行多步骤工作流的能力——要求我们从根本上重新思考软件设计。今天的软件是为人类构建的：图形界面、鼠标点击、应用之间的手动复制粘贴。AI 智能体被迫在这种以人为中心的环境中导航，浪费了大量资源，引入了安全漏洞，并产生了不可靠的结果。

**AFS（Agent-Friendly Standard，智能体友好标准）** 是一个开放规范，它颠覆了这一局面。AFS 不是让 AI 去适应人类软件，而是定义了软件应当如何从底层设计，使其成为 AI 智能体的好工具。AFS 提供了通用词汇、分层架构和轻量级约定，使任何服务或工具都能达到"智能体就绪"状态——实现安全、高效、可靠的交互。

本白皮书阐述了 AFS 的设计动机、核心设计哲学、技术架构以及在更广泛的 AI + 软件生态系统中的定位。规范性技术规格请参见 [`spec/overview.md`](../spec/overview.md)。

## 2. 问题：AI + 软件交互已经破碎

### 2.1 让 AI 操作人类界面代价高昂

当前的主流方法是让 AI "学会"使用人类软件——通过截图、模拟点击和浏览器自动化。这种方法有严重的局限性：

- **海量 Token 消耗**：AI 必须处理大型截图图像和 UI 元素元数据，导致成本极其高昂。
- **不可靠**：页面加载超时、按钮定位失败、布局变化和竞态条件导致频繁失败。智能体很容易陷入无限重试循环。
- **被主动抵制**：许多网站和应用部署了反机器人措施，导致账号封禁和访问限制。

### 2.2 每个应用各自内置 AI——碎片化的体验

当前的 SaaS 趋势是每个产品都嵌入自己的 AI 助手：Zoom 有自己的 AI，Miro 有自己的 AI，Qlik Sense 有自己的 AI。这造成了四个核心问题：

- **上下文碎片化**：十个应用意味着十个独立的 AI，彼此互不知晓。Zoom AI 总结了一场会议——但要让 Miro AI 根据这些笔记创建看板，需要手动复制粘贴。
- **重复计费**：用户在每个应用中为本质上相同的 LLM 能力分别付费。
- **质量参差不齐**：有些内置 AI 非常出色，有些则几乎不可用。用户别无选择。
- **厂商锁定**：Zoom 的 AI 只能操作 Zoom。跨应用编排不可能实现。

### 2.3 OpenClaw 的启示——方向正确，基础设施错误

OpenClaw（前身为 Clawdbot / Moltbot）是 2026 年初爆火的开源 AI Agent，GitHub 星标数超过了 Linux。它验证了用户对"一个 AI 智能体统治一切"的巨大需求。但 OpenClaw 也暴露了深层的基础设施缺陷：

- **Token 燃烧**：OpenClaw 通过浏览器和 bash 命令与人类软件交互。单个实例每天可消耗超过 5000 万个 API Token。这不仅成本巨大，而且向上下文窗口灌入了大量无关信息，降低了推理质量。
- **安全灾难**：OpenClaw 需要近乎完全的宿主权限——Shell 执行、文件系统访问、邮件和消息访问。一次通过恶意邮件发起的提示注入攻击，就可能导致智能体泄露密钥、删除数据或执行任意代码。安全研究人员已识别出超过 40,000 个漏洞；微软、思科和卡巴斯基都已发出警告。
- **技能生态污染**：OpenClaw 的技能市场（ClawHub）已成为恶意代码的温床。Snyk 的审计显示，超过 36% 的技能含有安全缺陷，其中 13.4% 为严重级别——包括恶意软件分发和凭证窃取。根本原因：技能只是 Markdown 文件，上传门槛几乎为零，没有代码签名，也没有安全审查。

**根本原因**不在于"一个 AI 管一切"的愿景——而在于 OpenClaw 使用的是*人类工具*来编排一切。它直接操作浏览器、执行 bash、访问任意文件，因为没有专门为 AI 构建的友好工具。唯一的选择就是给予智能体系统级权限，使得爆炸半径无限大。

## 3. 核心愿景：一个 AI，所有工具

AFS 提出了一个根本性的倒置：

> **当前模式**："软件内嵌 AI"——AI 是每个应用的一个功能，被困在各自的孤岛中。
>
> **AFS 模式**："AI 调用软件"——AI 是编排中枢。软件回归其工具本质，由 AI 代表用户调用。

用户用自然语言描述意图。AI 智能体自主决定调用哪些工具、如何编排工作流，并在所有交互中无缝共享上下文。

AFS 同时也是 CFS —— **Claw-Friendly Standard（Claw 友好标准）**。OpenClaw 证明了需求；AFS 提供了供给。符合 AFS 标准的软件可以被 OpenClaw、Claude Code 或任何其他 AI 智能体安全高效地调用——不绑定任何单一平台。

## 4. 设计哲学：渐进式披露与 skill.md

### 4.1 面向 AI 的渐进式披露

渐进式披露（Progressive Disclosure）是经典的交互设计原则：不要一次性倾倒所有信息；按需逐步展示。AFS 将此原则应用于 AI-软件交互：智能体不需要预先"看到"工具的每一个功能。相反，它按需访问分层文档。

### 4.2 skill.md——软件的自我介绍

AFS 的核心创新是 **skill.md**——一个结构化的能力清单，伴随每个符合 AFS 标准的工具。它不是一个随意的 README，而是一个具有标准格式的机器可读文档，按渐进式披露层级组织：

| 层级 | 内容 | Token 成本 |
|------|------|-----------|
| **第 0 层——概述** | 工具功能的一句话描述 | 极低——支持快速相关性筛选 |
| **第 1 层——能力** | 可用 API、参数和返回格式 | 适中——在需要该工具时加载 |
| **第 2 层——示例** | 常见使用模式和工作流模板 | 按需加载，用于复杂场景 |
| **第 3 层——高级** | 边界情况、错误处理、性能调优 | 极少加载——仅用于深度排错 |

AI 智能体读取第 0 层来判断工具是否相关，读取第 1 层来了解如何使用，仅在必要时才读取第 2-3 层。每次交互消耗最少的 Token，而不是将整本手册塞入上下文。

### 4.3 user-best-practice.md——用户自定义工作流

除了开发者提供的 skill.md，AFS 还允许用户编写 **user-best-practice.md** 文件来定义自己的常用工作流。例如：*"每周一早上，查询上周的销售数据，找出下降最大的品类，生成报告，并发送邮件给我。"* AI 智能体读取此文件，像一个训练有素的助手一样执行任务，遵循用户的既定习惯。

### 4.4 与 OpenClaw 技能的核心区别

| 维度 | OpenClaw 技能 | AFS skill.md |
|------|--------------|--------------|
| **本质** | 给智能体的指令（"如何使用人类工具"） | 工具的自我介绍（"我能做什么"） |
| **安全性** | 任意 Markdown；可包含恶意指令；36% 有安全缺陷 | 标准化格式 + 安全审查；仅描述 API 接口 |
| **Token 效率** | 无标准；智能体必须加载全部内容 | 渐进式披露；按需加载各层 |
| **通用性** | 仅限 OpenClaw 生态 | 任何 AI 智能体均可使用 |

## 5. 技术架构

### 5.1 系统概述

系统分为三个层级：

1. **用户层**：用户通过自然语言与独立的 AI 智能体交互。
2. **智能体层**：AI 智能体通过标准化 API 编排多个符合 AFS 标准的工具。
3. **工具层**：每个 AFS 工具（如 AFS-BI、AFS-Docs、AFS-Email）暴露结构化接口，并可选提供人类 UI。

### 5.2 每个 AFS 工具的三层接口

每个符合 AFS 标准的工具提供三个交互面，均由相同的核心逻辑支撑：

| 接口 | 受众 | 用途 |
|------|------|------|
| **API** | AI 智能体（主要） | 结构化输入输出，Token 高效，可靠 |
| **CLI** | 开发者 / 运维 | API 的薄封装，用于调试和脚本编写 |
| **人类 UI** | 终端用户 | 图形界面，面向偏好直接交互的用户 |

### 5.3 AFS 四层架构

| 层级 | 内容 | 解决的问题 |
|------|------|-----------|
| **第 1 层：接口** | 兼容 MCP 的结构化 API，具有明确的输入输出模式 | 统一通信标准；兼容现有生态 |
| **第 2 层：文档** | skill.md + user-best-practice.md，支持渐进式披露 | AI 按需获取信息；用户可自定义工作流 |
| **第 3 层：效率** | 紧凑响应格式、详细度开关、分页、流式传输 | 最小化 Token 消耗；最大化响应速度 |
| **第 4 层：安全** | 权限声明、危险操作确认、审计日志、回滚接口、代码签名 | 从根本上解决 OpenClaw 暴露的安全问题 |

## 6. 竞争分析

### 6.1 AI + 软件的四种方法

| 方法 | 代表 | 特点 |
|------|------|------|
| **屏幕级适配** | Computer Use, Operator | 零改造成本，但慢、贵、不可靠 |
| **智能体框架** | OpenClaw | 愿景出色，但通过人类工具烧 Token，安全漏洞严重，技能生态被污染 |
| **协议级适配** | MCP / Function Calling | 为现有软件添加接口，但不解决软件设计问题；响应质量不一致 |
| **软件级重新设计** ★ | **AFS** | 从设计层面为 AI 优化；最高效率和可靠性；兼容所有智能体平台 |

### 6.2 AFS 与 MCP：互补而非竞争

AFS 不是要取代 MCP——而是在 MCP 之上提高标准。打个比方：**MCP 好比 HTTP；AFS 好比 RESTful API 设计规范。** 每个 AFS 工具同时也是一个 MCP 服务器，但额外满足 AFS 在文档、效率和安全方面的质量要求。

### 6.3 AFS 与 OpenClaw：解决"巧妇难为无米之炊"问题

OpenClaw 是一个出色的 AI Agent 框架，但它面临着"巧妇难为无米之炊"的困境：它只能使用 bash、浏览器和原始 API 来完成任务，因为市场缺乏专门为 AI 智能体构建的工具。AFS 工具就是那些"食材"——它们使 OpenClaw（以及任何其他智能体）能够安全、高效、可靠地完成任务，而无需系统级权限。

## 7. 核心优势

### ① Token 节省——更低成本，更少能耗

通过结构化 API、紧凑响应格式和 skill.md 的渐进式披露设计，AFS 大幅减少了 Token 消耗。更短的上下文窗口意味着更低的成本、更快的响应和更高的 AI 推理质量。与 OpenClaw 每实例每天 5000 万以上 Token 的消耗相比，AFS 可以将等效任务的 Token 使用量降低一个数量级。

### ② 安全内建

OpenClaw 的安全问题不是 Bug——而是架构缺陷：它*必须*授予系统级权限才能运作。AFS 从根本上解决了这一问题：工具仅暴露有限的操作接口，实际操作由工具自身执行。即使遭受提示注入攻击，智能体也无法突破接口边界。智能体不再需要 bash 或文件系统访问；爆炸半径从"整个系统"缩小到"单个工具的 API 表面"。

### ③ 可靠性

结构化接口远比屏幕级操作或 bash 命令解析更可靠。不再有"按钮找不到"、"页面超时"或"输出格式变化"的故障。在企业场景中，这可能比 Token 节省更具说服力。

### ④ 共享上下文，跨工具协作

单一 AI 智能体编排所有工具，上下文自然共享。用户不再需要在不同应用的 AI 助手之间手动复制粘贴，也不再需要为每个应用单独付费。

### ⑤ 智能体无关，最大可移植性

AFS 工具不绑定任何特定智能体。无论是 OpenClaw、Claude Code、未来的 GPT Agent，还是任何新框架——只要它能读取 skill.md 并调用 API，就能使用 AFS 工具。这与 OpenClaw 封闭的技能生态形成了鲜明对比。

## 8. 市场策略

### 面向现有软件巨头的双轨战略

- **A 轨——适配层**：使用 MCP 适配器将现有软件的公开 API（Zoom、Miro 等）封装为 AFS 兼容接口。解决"能不能用"的问题。
- **B 轨——替代层**：在特定垂直领域构建 AFS 原生软件，提供比传统方案 10 倍的体验优势。解决"好不好用"的问题。

现实路径：**先 A 后 B，逐步替代。** 适配层解决可用性；原生软件解决质量。

## 9. 愿景：迈向 Agent OS 的第一步

我们正在见证一场不可逆的行业转变：从"软件 + 内嵌 AI"的捆绑模式，转向**AI 是入口和中枢，软件成为 AI 的插件**的新范式。

AFS 的终极愿景是成为 **Agent OS** 的基础层。正如操作系统定义了应用与硬件交互的规则，AFS 定义了 AI 智能体与软件工具交互的规则。随着更多软件采用 AFS，一个以 AI 为中心的软件生态将自然涌现——这就是 Agent OS。

在这个未来，用户只需一句话描述需求，AI 就能自动编排多个工具完成复杂工作流。没有上下文碎片化，没有重复计费，没有手动复制粘贴，没有安全噩梦。

**AFS 就是为这个未来书写规则的标准。**
